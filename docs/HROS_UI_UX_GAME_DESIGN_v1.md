# HROS UI/UX Game Design v1

Дата канонизации: 2026-07-30  
Статус: обязательный продуктовый и интерфейсный контракт  
Рабочее направление: **HROS COMMAND: Living World**

## 1. Назначение документа

Документ фиксирует решения по игровому UI/UX HROS, чтобы дальнейшая разработка не сводилась к отдельным декоративным экспериментам и не потеряла связь с идеологией продукта.

HROS должен ощущаться как живая персональная игра о человеке, отношениях, памяти и развитии, но оставаться проверяемой системой данных. Игровой слой отвечает за понятность, мотивацию, эмоциональную обратную связь и навигацию. Он не имеет права скрывать источник данных, присваивать человеку оценку или автоматически объявлять интерпретацию фактом.

## 2. Каноническая формула

```text
ИИ-дневник — основной вход
→ подтверждённая память
→ персонаж и роли
→ пути развития
→ мир людей и отношений
→ хроника
→ точные редакторы и аудит
```

Главный интерфейс HROS называется **COMMAND: Living World**.

Он объединяет:

- центр управления персонажем;
- живой диалог с ИИ-дневником;
- мир людей и отношений;
- редактор аватара;
- пути развития;
- хронику жизни;
- профессиональные редакторы данных.

## 3. Исследованные игровые источники

Анализ не означает копирование визуальных материалов, персонажей, интерфейсных ассетов или товарных знаков. HROS использует только общие UX-принципы.

### 3.1. Brawl Stars

Официальные источники:

- Quests: https://support.supercell.com/brawl-stars/en/articles/quests-3.html
- Starr Road: https://support.supercell.com/brawl-stars/en/articles/the-starr-road-2.html
- Records: https://support.supercell.com/brawl-stars/en/articles/records.html
- Currencies: https://support.supercell.com/brawl-stars/en/articles/currencies-2.html

Полезные принципы:

1. На главном экране есть очевидное следующее действие.
2. Нажатие на задание сразу переводит в нужный контекст.
3. Короткие задачи проще начать и закончить.
4. Путь развития можно сменить без потери накопленного прогресса.
5. Значимые достижения получают заметную, но короткую обратную связь.
6. Мобильная навигация использует крупные понятные цели касания.

Что переносится в HROS:

- один главный CTA на экране «Сегодня»;
- добровольные миссии;
- прямой переход из миссии в дневник, путь, аватар или момент;
- короткое подтверждение достижения;
- активный путь с возможностью переключения;
- ясная нижняя мобильная навигация.

Что запрещено переносить:

- FOMO;
- штраф за паузу;
- обязательные ежедневные серии;
- лутбоксы;
- платные ускорители психологического или relational-прогресса;
- множество валют;
- постоянные рекламные маркеры и красные точки.

### 3.2. The Battle of Polytopia

Официальные источники:

- Official site: https://polytopia.io/
- Tech Tree: https://polytopia.io/polytopia-switch/
- Nintendo product page: https://www.nintendo.com/us/store/products/the-battle-of-polytopia-switch/

Полезные принципы:

1. Большая система может быть представлена через чистую low-poly-карту.
2. На экране одновременно показывается ограниченное количество объектов.
3. Детали появляются после выбора объекта.
4. Дерево технологий объясняет направления развития.
5. Мир делится на визуально понятные области.
6. Сложность раскрывается постепенно.

Что переносится в HROS:

- low-poly-язык для мира и аватара;
- области жизни как территории: семья, работа, здоровье, творчество, знания;
- progressive disclosure;
- путь развития как дерево;
- крупные узнаваемые узлы вместо инженерной диаграммы;
- Web3D как режим исследования, а не единственный рабочий интерфейс.

Что запрещено переносить:

- представление отношений как захвата территории;
- соревнование за контроль над людьми;
- близость как ресурс;
- победу одного участника над другим.

### 3.3. Hero Wars

Официальный источник:

- Hero Skins: https://support-hwa.nexters.com/hc/en-us/articles/6116447672850-Hero-Skins

Полезные принципы:

1. Персонаж имеет несколько отдельных слоёв развития.
2. Внешний облик отделён от накопленного развития.
3. Один персонаж сохраняет непрерывность при смене формы.
4. Модификаторы и экипировка видимы в одной карточке.
5. Пользователь может подробно рассмотреть источник усиления.

Что переносится в HROS:

- многослойная карточка аватара;
- базовая форма, активная роль, модификаторы и история форм;
- отдельные слоты визуальных символов;
- сохранение старых форм;
- возврат к источнику появления модификатора.

Что запрещено переносить:

- общий Power Score человека;
- бесконечную прокачку ради цифры;
- десятки ресурсов;
- усиление человека покупкой;
- визуальную деградацию личности после конфликта;
- случайное получение значимых личных символов.

### 3.4. The Sims

Официальные источники:

- Features: https://www.ea.com/games/the-sims/the-sims-4/features
- Create a Sim: https://www.ea.com/en/games/the-sims/the-sims-4/new-player-hub/create-a-sim
- Live Mode: https://www.ea.com/games/the-sims/the-sims-4/new-player-hub/live-mode
- Modes reference: https://www.ea.com/games/the-sims/the-sims-4/faq/cheats

Полезные принципы:

1. Персонаж создаётся до погружения в сложную систему.
2. Внешность, роли и стремления доступны в прямом редакторе.
3. Разные режимы решают разные задачи: создание, жизнь, строительство.
4. Стремление направляет пользователя, но может быть заменено.
5. Жизненная история формируется из событий и отношений.
6. Прямое редактирование снижает когнитивную нагрузку.

Что переносится в HROS:

- создание базового аватара;
- режим «Сегодня» как Live Mode;
- режим «Аватар» как Create a Self;
- режим «Система» как Build Mode для точных данных;
- пути вместо обязательных квестов;
- хроника как история жизни;
- возвращение к последнему незавершённому действию.

Что запрещено переносить:

- симуляцию чувств как факта;
- автоматическое решение того, чего хочет человек;
- самостоятельное изменение состояния отношений;
- подмену подтверждённых данных игровыми показателями.

## 4. Формула влияния референсов

```text
40% The Sims
25% Brawl Stars
20% Polytopia
15% Hero Wars
```

Это не формула визуального копирования. Это распределение продуктовых принципов:

- The Sims — персонаж, роли, режимы, жизнь и редактирование;
- Brawl Stars — темп, главный CTA, мобильная ясность и короткие миссии;
- Polytopia — low-poly-мир, карта и дерево направлений;
- Hero Wars — глубина карточки персонажа и история форм.

## 5. Информационная архитектура

### 5.1. Сегодня

Главный экран должен отвечать на вопрос: **что имеет смысл сделать сейчас?**

Обязательные блоки:

- персонаж и активная роль;
- активный путь;
- один главный CTA;
- состояние незавершённой diary session;
- добровольные действия;
- ближайшие люди и отношения;
- последние подтверждённые моменты.

Приоритет CTA:

```text
Change Set ждёт подтверждения
→ Проверить изменения

Есть активный diary draft
→ Продолжить диалог

Нет активной сессии
→ Начать живой диалог
```

### 5.2. Дневник

Основной источник данных HROS.

```text
Диалог
→ изолированный draft
→ анализ
→ Change Set
→ ручная проверка
→ подтверждение
→ commit
```

Игровой интерфейс не изменяет этот контракт.

### 5.3. Мир

Пространственная карта:

- люди;
- отношения;
- области жизни;
- моменты;
- направления действий;
- уверенность и спорность данных.

Мир должен быть визуально простым. Точные значения и редактирование открываются во втором слое.

### 5.4. Аватар

```text
Identity Core
→ Base Avatar
→ Role Shell
→ Interest Modifiers
→ Relationship Context
→ Appearance Version
```

Пользователь вручную выбирает базовый вид. Отношения меняют ауру, окружение и совместные символы, но не определяют лицо, тело, ценность или личность человека.

### 5.5. Пути

Пути объединяют принципы Aspirations и Tech Tree.

Примеры:

- AI-создатель;
- физическая форма;
- партнёрство;
- отцовство;
- руководство;
- путешествия;
- творчество.

Переключение пути не удаляет предыдущий прогресс.

### 5.6. Хроника

Хронология включает:

- подтверждённые моменты;
- главы;
- изменения ролей;
- версии аватара;
- появление принципов;
- источники и статус уверенности.

Хроника не превращает гипотезу в сюжетный факт.

### 5.7. Система

Профессиональный слой:

- люди;
- моменты;
- знания;
- режим пары;
- книга;
- диагностика;
- версии;
- источники;
- privacy.

Игровой UI не заменяет точные редакторы.

## 6. Правила геймификации

### 6.1. Что может иметь прогресс

- роль;
- навык;
- проект;
- путь;
- привычка;
- подтверждённое действие;
- глава;
- коллекция моментов;
- изученная область жизни.

### 6.2. Что не может иметь прогресс или рейтинг

- ценность человека;
- качество партнёра;
- качество родителя;
- сила любви;
- успешность брака одной цифрой;
- полезность человека;
- послушание;
- готовность раскрывать приватные данные.

### 6.3. Мягкий ритм

HROS не использует стыд и страх потери серии.

Неправильно:

> Вы потеряли серию из 14 дней.

Правильно:

> Последняя сессия была несколько дней назад. Продолжить можно с сохранённого контекста.

### 6.4. Объяснимые награды

Любой открытый модификатор должен иметь:

- основание;
- source IDs;
- тип записи;
- дату;
- confidence;
- пользователя, подтвердившего изменение.

## 7. Visual Design System

### 7.1. Три тестовых темы

Одна UX-архитектура тестируется в трёх визуальных вариантах.

#### Family

- светлый фон;
- мягкий зелёно-бирюзовый акцент;
- спокойные поверхности;
- семейное и дневниковое восприятие.

#### Adventure

- тёмный фон;
- фиолетовый акцент;
- более выраженная игровая атмосфера;
- режим исследования и развития.

#### Strategy

- нейтральный светло-серый фон;
- сине-бирюзовый акцент;
- высокая информационная ясность;
- основной кандидат для повседневной работы.

### 7.2. Low-poly avatar

Первая версия использует процедурную CSS/Three.js-совместимую геометрию, а не реалистичный цифровой двойник.

Причины:

- независимость от внешних ассетов;
- быстрый playtest;
- модульность;
- низкая стоимость рендера;
- возможность позднее перейти на GLB/VRM без изменения доменной модели.

### 7.3. Progressive disclosure

На первом экране показывается:

- название;
- текущее состояние;
- одно действие;
- краткая причина.

Источник, версии, evidence и полный редактор открываются по запросу.

## 8. UX-потоки

### 8.1. Основной цикл дня

```text
Открыть HROS
→ увидеть одно главное действие
→ начать или продолжить дневник
→ проверить Change Set
→ подтвердить
→ получить смысловой результат
→ при необходимости открыть новый визуальный элемент
```

### 8.2. Смена пути

```text
Открыть Пути
→ сравнить направления
→ увидеть основания прогресса
→ выбрать новый активный путь
→ сохранить историю прежнего пути
```

### 8.3. Смена аватара

```text
Открыть Аватар
→ выбрать базовый вид
→ выбрать роль
→ включить или выключить модификаторы
→ выбрать relationship context preview
→ сохранить Appearance Version
→ при необходимости восстановить предыдущую форму
```

### 8.4. Переход к точным данным

```text
Игровая карточка
→ открыть источник или Систему
→ точный редактор
→ версия / статус / confidence / privacy
→ сохранить
→ вернуться в игровой слой
```

## 9. Accessibility

Обязательно:

- клавиатурная навигация;
- видимый focus;
- native controls;
- масштабируемый текст;
- достаточный контраст;
- адаптация до ширины 320 px;
- отдельная мобильная навигация;
- reduced motion;
- отсутствие критической информации только в цвете;
- отсутствие обязательных быстрых реакций и таймеров.

## 10. Skill contract

Интерфейс реализуется через skill `hros-game-interface-director`.

Каждое изменение должно проходить:

```text
UX goal
→ screen responsibility
→ primary action
→ information hierarchy
→ game mechanic safety check
→ accessibility check
→ responsive implementation
→ browser acceptance
→ playtest feedback
```

## 11. Playtest build 1

В первую тестовую сборку входят:

- новая игровая навигация;
- экран «Сегодня»;
- один основной diary CTA;
- карточка персонажа;
- схематичный Living World;
- добровольные миссии;
- редактор процедурного аватара;
- роли и модификаторы;
- локальная галерея Appearance Versions;
- пути развития;
- хроника;
- раздел точных системных редакторов;
- три темы;
- reduced motion;
- адаптивный desktop/mobile layout.

### 11.1. Ограничения playtest

- avatar settings хранятся отдельно в LocalStorage;
- они не являются новой доменной онтологией;
- progress path — только интерфейсный индикатор числа связанных confirmed/observed записей;
- внешний LLM не подключён;
- real GLB/VRM avatar не подключён;
- совместный multiplayer/avatar sharing не реализован.

## 12. Критерии тестирования

1. Пользователь за пять секунд находит главное действие.
2. Главный CTA открывает нужное состояние дневника.
3. Навигация понятна без обучения.
4. Все прежние редакторы доступны.
5. Theme switch не меняет UX-поток.
6. Reduced motion работает.
7. Avatar Core визуально отделён от оболочки.
8. Relationship Context не меняет ценность персонажа.
9. Путь можно переключить без удаления прогресса.
10. Старая форма аватара восстанавливается.
11. Mobile UI не требует горизонтальной прокрутки.
12. Chromium и WebKit не показывают console errors.

## 13. Следующий этап после playtest

После выбора визуальной темы и проверки UX:

1. канонизировать Avatar Ontology;
2. добавить Avatar Change Set;
3. перенести Appearance Version в Repository Service;
4. добавить server-side API;
5. подключить Three.js procedural humanoid;
6. связать модификаторы с подтверждёнными HROS records;
7. добавить source inspector;
8. провести отдельный playtest с близкими пользователя.
